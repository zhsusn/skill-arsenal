# self-check（产出物自查引擎）使用手册

> 版本：V2.1  
> 适用 Skill：`skills/sdlc/self-check`  
> 一句话定位：**阶段完成后，强制给你的产出物做一次全面体检，有重病（BLOCKER）不准走。**

---

## 1. 这是什么？

`self-check` 是你的 AI 项目「质量守门员」。每当你完成一个阶段（比如写完需求文档、做完设计、测完功能），它会自动或按你的指令，对阶段产出物做一次系统化的质量审查，输出一份**结构化自查报告**。

它像一个严格的质检员，但不会情绪化——发现问题就列出来，严重问题直接拦下，不让你进入下一阶段。

---

## 2. 适用场景

以下场景，**强烈建议**触发 `self-check`：

- ✅ 刚写完一份 PRD / 详细需求文档，想确认有没有漏写交互边界。
- ✅ 技术设计文档写完了，担心接口定义和实际需求对不上。
- ✅ 代码写完了准备提交，想先自查一遍内容一致性和内部矛盾。
- ✅ 测试用例写完了，不确定覆盖率够不够、断言有没有写废。
- ✅ UAT 做完了，需要生成一份正式的验收报告质量检查。
- ✅ 项目收尾阶段，要对全部历史产出物做批量审计。

一句话：**任何你觉得"应该再检查一下"的时候，就叫它。**

## 3. 核心功能

### 3.1 八维质量扫描（V2.1 最新）

| 维度 | 通俗解释 |
|------|----------|
| **内容一致性** | 你写的东西和上游需求/设计是不是一致的？有没有偷偷改了需求没更新文档？ |
| **内容完整性** | 该写的章节写全了吗？必填字段填了吗？附件挂了吗？ |
| **交叉引用有效性** | 文档里引用的链接、ID、版本号，点一下还能用吗？ |
| **无内部矛盾** | 同一份文档里，前面说东后面说西，自己打自己脸了吗？ |
| **接口一致性** | API 定义和代码实现是不是一回事？前后端对好了吗？ |
| **覆盖率/测试有效性** | 测试用例真的测到需求点了吗？有没有"假装在测试"的无效用例？ |
| **交互规格完整性** | 详细需求里，交互流程、异常分支、边界条件都定义清楚了吗？（V2.1 新增） |
| **UAT 报告质量** | 验收结论站得住脚吗？缺陷分级合理吗？遗留风险说明白了吗？（V2.1 新增） |

### 3.2 三级红绿灯

每个发现的问题都会被标上一盏灯：

- 🔴 **BLOCKER（红灯）**：这是硬伤，必须修好才能走。比如需求矛盾、接口对不上、硬编码了密码。
- 🟡 **WARNING（黄灯）**：有风险，建议修，但不强制拦你。比如文档格式不统一、某个边界条件没写清楚。
- 🟢 **INFO（绿灯）**：仅供参考的小建议。比如"这里可以补个例子"、"建议用更明确的措辞"。

**门控规则很简单：有红灯，就不给过。**

### 3.3 覆盖 12 个阶段

从需求到收尾，全生命周期都能查：

`需求概要 → 详细需求 → 技术设计 → 接口设计 → 数据库设计 → 开发实现 → 单元测试 → 集成测试 → UAT → 发布准备 → 部署上线 → 项目收尾`

## 4. 使用方式（完整示例）

### 4.1 基本用法：阶段完成后自动触发

当你在对话中明确表达某个阶段已完成时，`self-check` 会自动激活。例如：

**你说：**
> "详细需求文档已经写完了，帮我检查一下。"

**Skill 行为：**
1. 识别当前阶段为「详细需求」。
2. 加载该阶段对应的检查维度（D1, D2, D3, D4, D7）。
3. 对你的文档执行原子化验证。
4. 输出结构化自查报告。

### 4.2 显式触发：随时自查

如果你不想等自动触发，可以直接发指令：

**你说：**
> "/self-check 对当前 PRD 进行内容完整性和一致性检查。"

或：

> "请对这份接口设计文档做一次全面的自查，重点关注接口一致性。"

### 4.3 实战示例：详细需求阶段自查

**场景**：你刚写完一份用户注册的详细需求文档。

**对话：**

> **你**：详细需求写完了，帮我自查一下。
>
> **AI**：收到，正在对「详细需求」阶段产出物执行 self-check（V2.1）。检查维度：内容一致性、内容完整性、交叉引用有效性、无内部矛盾、交互规格完整性。
>
> **AI**：检查完成。门控结果：**REJECT（存在 BLOCKER）**。
> - 总检查项：35
> - 通过：30 | 失败：5
> - BLOCKER：1 | WARNING：3 | INFO：1
>
> ---
>
> **🔴 BLOCKER**
> #### [D4-REQ-007] 无内部矛盾
> - **位置**：`user-registration-detail.md:42`
> - **证据**：第 42 行规定"密码长度 8-20 位"，但第 89 行异常处理章节写的是"密码过短时提示'长度不能小于 6 位'"
> - **建议**：统一密码最小长度策略，建议以 8 位为准，同步修正异常提示文案。
>
> **🟡 WARNING**
> #### [D2-REQ-012] 内容完整性
> - **位置**：`user-registration-detail.md`
> - **证据**：缺少「手机号已注册」场景的异常分支交互定义。
> - **建议**：补充该异常分支的状态转移与前端提示文案。
> ...（其余 3 个 WARNING 省略）...
>
> **下一步行动**：
> 1. 修复上述 1 个 BLOCKER（密码长度矛盾）。
> 2. 确认或修复 3 个 WARNING。
> 3. 对我说"已修复，重新检查"，我将再次运行 self-check。

**你的后续操作：**

> **你**：已修复密码长度矛盾，补充了手机号已注册场景。请重新检查。
>
> **AI**：重新检查完成。门控结果：**PASS**。
> - BLOCKER：0 | WARNING：1（已记录） | INFO：1
> - 可以进入下一阶段：技术设计。

### 4.4 实战示例：UAT 阶段自查

**场景**：UAT 测试结束，你需要生成验收报告并检查其质量。

**对话：**

> **你**：UAT 做完了，帮我检查一下验收报告的质量。
>
> **AI**：正在执行 UAT 报告质量检查（维度 D8）。
>
> **AI**：检查完成。门控结果：**CONDITIONAL_PASS**。
> - 未发现 BLOCKER。
> - WARNING：2（缺陷分级描述不够具体；遗留风险缺少缓解计划）
> - 建议修复 WARNING 后归档，但不阻塞发布流程。

## 5. 输出产物说明

每次 `self-check` 都会生成一份 **结构化自查报告**，通常命名为 `self-check-report-{阶段}-{时间}.md`。

报告里有什么：

| 章节 | 内容 |
|------|------|
| **元信息** | 阶段名称、检查时间、Skill 版本、最终门控结果。 |
| **摘要统计** | 总共查了多少项、通过多少、失败多少、各级严重度数量。一眼看出健康度。 |
| **详细发现** | 按 BLOCKER / WARNING / INFO 分组，每一项都告诉你：**在哪儿、什么问题、证据是什么、怎么改**。 |
| **下一步行动** | 根据门控结果给你明确的后续指令，不用猜。 |

**报告的价值：**
- 作为阶段评审会的材料附件。
- 作为项目经理追踪质量问题的依据。
- 作为发布清单的合规证明。

## 6. 常见问题

### Q1：BLOCKER 真的不能跳过吗？

**不能。** 这是 `self-check` 的核心设计原则——零信任。如果你确实遇到特殊情况，正确的做法是：修复它，或在上游变更需求/设计后，用更新后的基准重新检查。不要试图"说服"检查器忽略事实错误。

### Q2：WARNING 可以不管吗？

**可以进入下一阶段，但不建议长期忽视。** WARNING 代表潜在风险，积少成多会变成技术债务。建议至少排期修复，或在报告中记录接受风险的理由。

### Q3：检查要花多久？

取决于产出物的篇幅和阶段。一份 10 页的详细需求通常几十秒到几分钟。如果感觉太久，可以对 AI 说"先重点检查 BLOCKER 级问题"，快速拿到门控结论。

### Q4：我修改了一小部分，需要全部重查吗？

目前 V2.1 执行全量检查。你可以要求"仅检查我修改的部分"（增量检查），AI 会尽量聚焦变更范围，但完整门控仍需全量通过一次。

### Q5：报告存在哪里？

默认输出在对话中。如果你需要文件留存，可以说"将报告保存为 `self-check-report.md`"，AI 会写入当前工作目录。

### Q6：为什么有时候检查维度不一样？

不同阶段激活的检查维度不同。例如「开发实现」阶段不会检查「UAT 报告质量」，「UAT 阶段」也不会检查「交互规格完整性」。这是按阶段裁剪的，不是漏查。

## 7. 快速参考卡

### 7.1 触发口令

| 你想做什么 | 怎么说 |
|-----------|--------|
| 阶段完成后自动检查 | "XX 写完了，帮我检查一下。" |
| 显式触发 | "/self-check" 或 "请对当前产出物执行自查。" |
| 指定维度检查 | "重点检查内容一致性和内部矛盾。" |
| 重新检查 | "已修复，请重新检查。" |
| 保存报告 | "将自查报告保存为文件。" |

### 7.2 严重度速查

| 图标 | 级别 | 含义 | 是否阻塞 |
|------|------|------|----------|
| 🔴 | BLOCKER | 事实错误、内部矛盾、关键缺失 | **是** |
| 🟡 | WARNING | 潜在风险、规范偏离 | 否（需确认） |
| 🟢 | INFO | 建议、优化提示 | 否 |

### 7.3 门控结果速查

| 结果 | 含义 | 你能做什么 |
|------|------|-----------|
| **PASS** | 全部通过，或有 INFO 级建议 | 放心进入下一阶段 |
| **CONDITIONAL_PASS** | 有 WARNING，无 BLOCKER | 可以进入下一阶段，但建议修复 WARNING |
| **REJECT** | 存在 BLOCKER | 必须修复后重新检查 |

---

> 💡 **使用心法**：`self-check` 不是找茬，是帮你省钱——在阶段内部发现问题，比在上线后修复便宜 100 倍。养成习惯：**阶段完成 → 自查 → 修问题 → 再走**。这就是专业交付的节奏。
