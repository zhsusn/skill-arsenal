# PRD-000 概要需求生成器 — 使用手册

> **Skill 版本**：V2.1  
> **适用阶段**：OpenSpec 阶段 2（概要需求生成）  
> **关联 Skill**：`brainstorming`、`competitive-analysis`、`requirement-analysis`、`high-level-design`、`detailed-requirements`、`progress-tracker`、`self-check`、`human`  
> **更新日期**：2026-05-08

---

## 一、这是什么

**prd-generation** 是你的「需求基线建筑师」。

当你要从零开始规划一个新产品、新系统或大型功能集时，它会通过**四层递进式对话**帮你把模糊的想法转化为**结构清晰、逻辑自洽、不可推翻**的需求基线。整个过程就像一位经验丰富的产品经理在 Interview 你——但它不会一次性丢给你 50 个问题，而是层层深入，每层确认信息足够完整后才进入下一层。

最终产出是 **5 个 Markdown 文件**（OpenSpec 规范），它们将成为后续详细需求、概要设计、技术实现的全局约束。任何下游阶段发现「这里需求没说清楚」，都可以回溯到这五份文件找答案。

> 💡 **一句话理解**：prd-generation 负责回答「为什么做、为谁做、做什么、不做什么、做到什么程度」这五个根本问题，并且让你签字确认后才算数。

## 二、适用场景

### ✅ 什么时候用它

- **从零开始**："我们要做一个 AI 短剧生成平台，先帮我理清需求"
- **建立基线**："这个项目需求太散了，帮我定一个不可推翻的基线"
- **项目启动前**："开始开发前，我需要一份所有人都认可的 Scope 和功能边界"
- **避免返工**："上次项目做到一半发现需求矛盾，这次想提前拦住"
- **Brainstorming 之后**："我们已经头脑风暴完了，把这些想法变成结构化 PRD"

### ❌ 什么时候不用它

- **补写 PRD**：已经开发到一半再补需求文档 → 应走变更流程，而非重新生成基线
- **单个功能详细规格**："帮我写一下登录功能的详细交互" → 用 `detailed-requirements` 的单模块模式
- **纯技术预研**：没有明确业务目标的技术调研 → 先用 `brainstorming` 探索价值

## 三、核心功能

| 功能 | 说明 | 对你意味着什么 |
|------|------|--------------|
| **四层递进对话** | 按 Layer 1→2→3→4 逐步访谈 | 你不需要一次性回答所有问题，每次只聚焦一个主题 |
| **红绿灯评分** | 每层结束后量化评分，< 90 分阻塞 | 信息不全时 AI 会拦住你，而不是带着漏洞继续前进 |
| **JTBD 需求提炼** | 把"功能清单"变成"用户为什么需要" | 防止做出「技术上很酷但用户无感」的功能 |
| **强制一致性校验** | 输出前自动检查 8 项内部一致性 + 3 项竞品对标 | 在写代码之前就发现"Out-of-Scope 写了不做支付，In-Scope 却要卖会员"这种矛盾 |
| **五文件输出** | 01~05 五个 Markdown 文件 | 下游 Skill 可以按需读取，不用加载一份 300 行的超大文档 |
| **🚪 Gate 1 人工冻结**（V2.1 新增） | 五文件输出后 AI 自动宣读阻塞提示，等待你签字确认 | AI 不会偷偷帮你"确认"，必须由你亲自审阅后冻结基线 |
| **基线不可推翻** | 冻结后 Scope/NFR/核心实体在详细阶段不可修改 | 开发中途不会突然冒出"这个需求好像 PRD 里没写"的争议 |

## 四、使用方式

### 4.1 启动方式

**方式一：自然语言触发（推荐）**

```
💫 我要做一个 AI 短剧生成平台，帮我写一下概要需求
```

```
💫 基于 brainstorming 结果，帮我生成 PRD-000
参考文档：@openspec/changes/短剧平台-v1/proposal.md
```

**方式二：斜杠命令触发**

```
/skill:prd-generation 为 reelforge 变更生成概要需求
```

**方式三：通过 /opsx:propose 触发（若已配置 OpenSpec）**

```
/opsx:propose "为 reelforge 增加 AI 剧本分镜自动生成功能"
```

### 4.3 各阶段配合要点

| 阶段 | 你需要做什么 | 不要做什么 |
|------|-------------|-----------|
| **Layer 1** | 回答每个问题，尽量具体（用数据、用场景） | 不要说"你懂的"或"按行业常规来" |
| **Layer 2** | 明确说"不做什么"（Out-of-Scope 和 In-Scope 同等重要） | 不要跳过 Out-of-Scope 问题 |
| **Layer 3** | 给出可量化的数字（当前值 vs 目标值） | 不要说"尽量快""体验好" |
| **Layer 4** | 认真看 AI 发现的矛盾，选择修正或接受风险 | 不要闭眼点"没问题" |
| **Gate 1** | 逐文件快速浏览，确认关键信息无误 | 不要一句话都不看就确认冻结 |

## 六、常见问题

**Q1：为什么 AI 不一次性把所有问题问完？**
> 四层递进的设计目的是「每层信息完整后再进入下一层」。如果一次性问完，你可能会在信息不全的情况下做出错误判断，导致后续大规模返工。就像盖楼——地基没打牢就往上盖，后期修补成本极高。

**Q2：评分 < 90 分一定要补充吗？能不能跳过？**
> 强烈建议补充。如果某维度确实无法提供（比如你们真的是全球首创、无竞品），你可以明确说"无竞品，标记为已知缺失"，AI 会降权处理。但其他缺失项仍需补充。

**Q3：Layer 4 发现严重问题，AI 会自己修吗？**
> **不会**。AI 只会列出问题清单和修正建议，等待你确认后才修改。这是为了防止 AI 误解你的意图而擅自改动需求——比如它可能以为"会员购买"应该改成"免费"，但你实际想的是"接入 Stripe 只是放在 Phase 2"。

**Q4：Gate 1 我可以不确认，先去看看文件再回来吗？**
> 当然可以。Gate 1 是阻塞态，你随时可以提出修改意见，AI 修正后会重新进入 Step 5 输出。直到你明确说"确认冻结"，基线才不会锁定。

**Q5：冻结后发现 Scope 漏了一个功能怎么办？**
> 需要通过 `human` Skill 记录变更决策，升版五文件至 v1.1+，并通知所有下游 Skill 重新校验。不能直接偷偷改文件——否则 downstream 会以为基线没变。

**Q6：没有 OpenSpec 环境能用吗？**
> 可以运行，但 AI 会提示你初始化 OpenSpec 目录。没有 `config.yaml` 时，Skill 会使用内置默认模板输出，只是少了 `required_sections` 的刚性对齐校验。

**Q7：和旧版 `prd-system-outline` 有什么区别？**
> `prd-system-outline`（V1.x）输出单文件 PRD-000；`prd-generation`（V2.x）输出五文件（与 OpenSpec 深度集成），并增加了 JTBD 框架、Component Inventory、原子声明分解验证、Gate 1 人工冻结等机制。

### 7.2 下游接力指南

```
prd-generation (产出 5 文件)
    ├──→ competitive-analysis mode=technical（读取 01 第 3 章做技术深度对比）
    ├──→ high-level-design (读取 04/05 做概要设计)
    ├──→ detailed-requirements (读取 03 按模块生成 feature-XX-{模块}/)
    └──→ self-check (读取全部 5 文件执行最终校验)
```

### 7.3 质量检查清单（Gate 1 自检用）

在确认冻结前，快速扫一遍这 5 件事：

- [ ] **Scope 闭环**：Out-of-Scope 列出的东西，不会影响 In-Scope 的核心流程
- [ ] **P0 可测试**：每个 P0 需求都有对应的验收标准（Given/When/Then）
- [ ] **实体完整**：核心实体（如项目、用户、订单）有名称、主键、关系定义
- [ ] **NFR 有数**：性能/安全/并发指标都是具体数字，不是"尽量快"
- [ ] **模块名 OK**：03 里的模块名读起来没问题，因为详细阶段不能改
