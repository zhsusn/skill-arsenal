# functional-architecture-generator 设计与使用手册

> 本文档为内部设计参考，说明 `functional-architecture-generator` skill 的设计意图、核心决策、与原始版本的区别，以及使用方式。

## 一、设计意图

在软件交付过程中，**业务功能架构图**是连接"需求"与"技术实现"的关键桥梁。但现有 skill（如 `high-level-design`）的 `system_architecture` 章节主要聚焦 C4-Model **技术架构**，缺少系统化的**业务功能架构**生成能力。

本 skill 填补这一缺口，提供：
- 从 PRD/需求文档推导业务域边界的**方法论**
- 出版级可视化的**颜色编码策略**
- 可直接渲染的 Mermaid **布局规范**
- 完整的架构文档输出格式（划分说明 + 架构图 + 模块清单 + 关键说明）

## 二、演进历史

### 原始版本（v0.1，即本文件早期版本）
原始设计为一份强约束的"系统功能架构文档生成器"指令，存在以下问题：
- **布局强制不可变**：强制使用 `flowchart TB` + 内部左右两列嵌套 subgraph
- **Mermaid 渲染风险**：嵌套 subgraph 方向在 Mermaid v8.x 和部分 CI 渲染器中表现不稳定（参见 mermaid-js/mermaid #7477、#1751、#1726）
- **形式大于内容**：强制单一布局导致某些系统拓扑（扁平微服务、中台+多前台）被不合理地压缩为"细长瀑布图"

### skill 化改造（v1.0）
将原始指令改造为符合 `skill-arsenal` 规范的独立 skill，核心调整：

| 维度 | 原始版本 | skill 化后（当前） |
|------|---------|------------------|
| 布局 | **强制限定**，不可调整 | **推荐规范** + **布局决策树**，按需选择 TB/LR/单列/双列 |
| subgraph 嵌套 | 必须三级嵌套（TB→LR→TB） | 降级为**可选排版技巧**，注明版本兼容性风险 |
| 校验环节 | 无 | 新增**交付与校验**环节（mmdc / Kroki） |
| 输出物 | 只有 Mermaid 代码 | 完整四段式文档（划分说明 + 架构图 + 模块清单 + 关键说明） |
| 协作关系 | 独立指令 | 明确作为 `high-level-design` 的**业务架构补充** |

## 三、核心设计决策

### 决策 1：布局从"强制"改为"推荐+决策树"
**原因**：架构图的本质是信息传达，而非模板套用。不同系统拓扑天然适合不同布局。
- 分层架构（接入/业务/数据）→ TB
- 扁平微服务（Gateway → N 个平级服务）→ LR
- 模块数 ≤ 4 → 单列 TB
- 模块数 > 4 → 双列 LR 或拆分为二级 subgraph

### 决策 2：颜色编码策略保留并强化
原始版本的颜色编码是同色系渐变（大域背景 100-200 色阶 / 节点 50 色阶 / 描边 700-900 色阶），这是本 skill 的核心价值之一，直接保留。

语义化颜色映射（前台=红、管理=橙、核心服务=黄、数据=绿、外部依赖=蓝）符合中文互联网企业直觉，无需调整。

### 决策 3：与 `high-level-design` 形成上下游而非替代
- `high-level-design` 负责 **C4-Model 技术架构图**（Context→Container→Component）
- `functional-architecture-generator` 负责 **业务功能架构图**（业务域/用户角色/生命周期视角）
- 两者在 `high-level-design` 的 `system_architecture` 章节中以**双视图**形式并存

## 四、使用手册

### 触发场景
当用户提到以下关键词时触发：
- "画架构图"、"系统功能架构"、"模块划分"
- "业务域拆分"、"功能模块归类"
- "基于 PRD 做架构"、"需求转架构"

### 输入
- **必须**：PRD-000（`specs/01-05.md`）或详细需求文档
- **可选**：已有模块清单（`03-functional-structure.md`）

### 输出
四段式标准化文档：
1. **架构划分说明**：划分视角 + 分区列表（名称/定位/模块数/色系）
2. **系统架构总览**：可直接渲染的 Mermaid 代码（含 classDef + subgraph + style + 流向箭头）
3. **模块清单表**：分区 × 模块名称 × 功能职责 × 对应需求章节 × 依赖/被依赖
4. **关键架构说明**：核心中枢模块、跨分区交互、外部依赖

### 执行步骤
1. 读取需求文档，识别功能点
2. 选择 1-2 个划分视角（用户角色/业务域/系统层级/内外部边界/生命周期）
3. 按分区原则划分 3-6 个分区
4. 为每个分区分配色系（参考颜色编码表）
5. 按布局决策树选择 Mermaid 布局方向
6. 生成 Mermaid 代码
7. **语法校验**（mmdc 或 Kroki）
8. 输出完整文档（默认嵌入 Markdown；如需独立图片，调用 `mermaid-diagrams` 导出）

### 与下游 skill 的衔接
| 下游 | 衔接点 |
|------|--------|
| `mermaid-diagrams` | 需要导出 PNG/SVG/PDF 时，调用其工具链 |
| `high-level-design` | 业务功能架构图作为 `system_architecture` 的可选子视图嵌入 |
| `detailed-design` | 模块清单表中的模块名称和职责，作为详细设计的输入 |

## 五、注意事项

- **不虚构模块**：所有模块必须能在需求文档中找到原文支撑
- **粒度控制**：单个分区 4-8 个模块，超过需合并为子系统
- **Mermaid 兼容性**：嵌套 subgraph 方向在旧版渲染器中可能异常，建议优先使用单层 subgraph + 节点分组
- **颜色对比度**：确保打印（黑白）时仍能区分区域边界
