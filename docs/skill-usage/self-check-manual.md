# Self-Check Skill 使用手册

> 本文档面向 Skill 使用者，提供触发方式、各阶段指令速查、报告解读与常见问题。

---

## 1. 快速开始

### 1.1 什么是 Self-Check？

`self-check` 是贯穿软件全生命周期的**产出物质量门控**。在每个阶段完成后，它对当前产出物进行系统性自查，确保：

- 与上游文档没有矛盾
-  required_sections 没有遗漏
- 文档间的 `@引用` 和链接都能解析
- 同一文档内没有逻辑冲突
- 代码与接口契约一致（编码阶段）
- 测试真正在验证行为，而非制造虚假信心（测试阶段）

**核心原则**：不自查，不流转。存在 BLOCKER 时严禁进入下一阶段。

### 1.2 触发方式

| 方式 | 指令示例 |
|------|----------|
| 通用触发 | `/self-check` |
| 通用触发 | 【自查 \| Skill：self-check】 |
| 阶段触发 | 【阶段 3 自查 \| Skill：self-check】请检查架构是否覆盖所有 P0 模块... |

## 2. 各阶段触发指令速查

| 阶段 | 建议指令 |
|------|----------|
| **阶段 2 概要需求** | 【阶段 2 自查】请检查与 proposal.md 一致性、required_sections 完整性、模块划分合理性 |
| **阶段 2.5 详细需求** | 【阶段 2.5 自查】请逐模块检查与概要需求一致性、spec/prototype/io-table/logic 完整性、模块间矛盾 |
| **阶段 3 概要设计** | 【阶段 3 自查】请检查架构覆盖 P0 模块、技术选型理由、与详细需求对应关系 |
| **阶段 4 详细设计** | 【阶段 4 自查】请检查数据库与数据架构一致性、API 与接口契约一致性、类设计覆盖功能点 |
| **阶段 5 接口驱动** | 【阶段 5 自查】请检查接口契约覆盖度、Mock 数据完整性、并行计划冲突 |
| **编码** | 【自测】请检查功能符合度、接口一致性、异常处理覆盖、单元测试通过 |
| **单元测试** | 【阶段 8 自查】请检查覆盖率≥70%、边界条件覆盖、测试独立性、反模式检测 |
| **集成测试** | 【阶段 9 自查】请检查端到端主链路覆盖、需求编号追溯、数据清理完整性 |
| **收尾** | 【最终自查】请检查所有产出物归档完整性、代码遗留问题、文档一致性 |

## 3. 检查项说明

### 3.1 内容一致性

**目的**：当前产出物与上游文档（前一阶段）没有矛盾。

**示例**：
- ✅ 概要需求写"系统面向 C 端用户"，详细需求也写"面向 C 端用户"
- ❌ 概要需求定义"角色最大 100 个"，详细需求写"批量创建上限 50 个"（数值矛盾）
- ❌ 上游提到"支持 OAuth2 登录"，当前文档未提及（缺失）

### 3.2 内容完整性

**目的**：当前产出物覆盖了 `config.yaml` 中该阶段要求的所有 `required_sections`。

**示例**：
- ✅ `high-level-design` 的 `required_sections` 包含 `system_architecture`，且 `01-system-architecture.md` 中有对应章节
- ❌ `data_architecture` 在 `required_sections` 中列出，但产出物中找不到对应内容

### 3.3 交叉引用有效性

**目的**：文档中 `@路径` 引用和 Markdown 链接都能正确解析。

**示例**：
- ✅ `@openspec/changes/{change}/specs/01-product-overview.md` 文件存在
- ❌ `@specs/03-functional-structure.md` 文件不存在或路径错误
- ❌ `[业务规则](rules.md#权限矩阵)` 的锚点 `#权限矩阵` 在目标文件中不存在

### 3.4 无内部矛盾

**目的**：同一文档内的逻辑自洽。

**示例**：
- ❌ 第 23 行定义"角色：系统中的虚拟演员"，第 78 行定义"角色：指代系统管理员"
- ❌ 状态机图中存在不可达状态或死循环
- ❌ 权限矩阵中同一角色对同一资源既有"读"又有"禁止读"

### 3.5 接口一致性（编码阶段）

**目的**：代码实现与 `api-spec.md` / `openapi.yaml` 完全一致。

**检查点**：
- 接口路径是否一致（如 `/api/v1/roles`）
- HTTP 方法是否一致（GET / POST / PUT / DELETE）
- 请求参数字段名、类型、必填性是否一致
- 响应结构字段名、类型是否一致
- 异常码是否都有对应的错误处理

### 3.6 覆盖率与测试有效性（测试阶段）

**目的**：测试不仅通过，而且真的能捕获回归。

**覆盖率门控**：总体覆盖率 ≥ 70%。

**Green Mirage 反模式检测**：
- 空断言：`assert True`
- 同义反复：`assert len(list) == len(list)`
- 过度 mock：mock 了被测对象的核心逻辑
- 检查实现而非行为：直接断言 `_internal_state`
- 无法失败的测试：测试路径无 assert

> **注意**：覆盖率 100% 但全是 Green Mirage，仍然视为 WARNING。

## 4. 报告解读

self-check 输出结构化 Markdown 报告，包含以下部分：

### 4.1 检查结果汇总

| 检查维度 | 通过数 | 失败数 | 警告数 | 状态 |
|----------|--------|--------|--------|------|
| 内容一致性 | 5 | 0 | 1 | ⚠️ |
| 内容完整性 | 4 | 1 | 0 | ❌ |
| 交叉引用有效性 | 6 | 0 | 0 | ✅ |

**状态图标含义**：
- ✅ 全部通过
- ❌ 存在失败项（至少一个 BLOCKER）
- ⚠️ 无失败，但存在 WARNING

### 4.2 阻塞问题（🔴 BLOCKER）

必须修复，否则禁止进入下一阶段。

示例：
```markdown
1. **feature-02-模块B 缺少 io-table.md**
   - **检查项**：content_completeness
   - **位置**：`openspec/changes/{change}/specs/feature-02-模块B/`
   - **问题描述**：required_sections 要求包含 io-table，但该模块未提供
   - **修复建议**：补充输入输出表，参考 feature-01 模板
```

### 4.3 警告（🟡 WARNING）

建议修复，可进入下一阶段但需记录风险。

### 4.4 通过项（✅）

列出关键证据，证明该检查点确实通过。

### 4.5 下一步行动

根据门控规则自动生成：
- 存在 BLOCKER → "请修复以上阻塞问题后，重新执行 self-check"
- 无 BLOCKER → "自查通过，可进入下一阶段"

## 5. 常见问题

### Q1：self-check 和 code-review 有什么区别？

| 维度 | self-check | code-review |
|------|------------|-------------|
| 触发时机 | 阶段完成后 | 提交前/重构时 |
| 检查对象 | 文档 + 代码 + 测试 |  primarily 代码 |
| 核心关注 | 一致性、完整性、引用有效性 | 安全、性能、可维护性 |
| 流程作用 | **阶段门控**（阻塞流转） | 建议优化 |

### Q2：发现 BLOCKER 后可以直接忽略吗？

**不可以**。self-check 的设计原则就是"不自查不流转"。BLOCKER 意味着产出物存在硬性缺陷，进入下一阶段会导致错误放大。必须先修复，然后**重新执行 self-check** 确认通过。

### Q3：为什么测试覆盖率 100% 还是报了 WARNING？

因为 self-check 不仅检查覆盖率数字，还使用 `auditing-green-mirage` 的反模式检测来验证**测试是否真的能捕获失败**。如果测试全是 `assert True` 或过度 mock，即使覆盖率 100%，也会被标记为 Green Mirage（虚假信心）。

### Q4：检查耗时太长怎么办？

5 个子 Agent 是并行执行的。如果仍然觉得慢，可以：
1. 缩小检查范围（指定具体文件而非整个目录）
2. 跳过可选检查（如 Mermaid 语法检查）
3. 分阶段执行（先只检查内容完整性，通过后再检查一致性）

### Q5：self-check 会自动修改我的文件吗？

**不会**。self-check 只输出报告，不自动修改任何产出物。所有修复需经用户确认后由其他 Skill（如 `executing-plans` 或用户手动）执行。

## 6. 速查卡

```text
触发：/self-check 或 【自查】
原则：零信任、证据溯源、原子化验证、测试必须能失败
门控：BLOCKER → 禁止流转 / WARNING → 记录风险 / 全过 → 允许流转
必含：一致性、完整性、引用有效性、内部矛盾
编码加：接口一致性
测试加：覆盖率≥70%、Green Mirage 检测
修复后：必须重新执行 self-check
```
