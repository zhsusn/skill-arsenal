# systematic-debugging（系统调试）使用手册

> 版本：V2.1  
> 适用 Skill：`skills/sdlc/systematic-debugging`  
> 一句话定位：**遇到 Bug 先别急着改，按四步走，找到根因再动手。**

---

## 1. 这是什么？

`systematic-debugging` 是你的"调试导航仪"。它不会替你写修复代码，但会强制你按一个经过验证的四阶段流程来思考问题，避免"改这里不行、改那里又出新问题"的无效循环。

这个 Skill 的核心信条很简单：
> **没找到根因之前，不许动手修复。**

V2.1 版本新增了与项目进度系统的联动：如果根因实在找不出来，它会帮你把问题登记为技术债务，而不是假装已经修好了。

---

## 2. 适用场景

以下场景，强烈建议使用：

- ✅ 测试突然失败了，你不确定为什么。
- ✅ 线上出现了 Bug，日志里有报错。
- ✅ 代码行为不符合预期，但看起来"应该没问题"。
- ✅ 性能突然下降，怀疑是某个改动导致的。
- ✅ 构建/部署失败了，错误信息很模糊。
- ✅ 集成测试通不过，不确定是哪个模块的问题。
- ✅ 你已经试了两次修复都没成功，开始有点慌了。

**不适合的场景**：
- ❌ 你想学习某个框架的调试技巧（这不是通用教程，是工作流纪律）。
- ❌ 代码完全没问题，你只是想做重构（请用 `requesting-code-review`）。

## 3. 核心功能

### 3.1 四阶段调试流程

这个 Skill 把调试拆成了四个必须按顺序完成的阶段：

| 阶段 | 你要做什么 | 完成标准 |
|------|-----------|----------|
| **Phase 1: 根因调查** | 读报错、复现问题、查近期变更、追踪数据流 | 你能说清楚"为什么会出这个问题" |
| **Phase 2: 模式分析** | 找同类工作的正确代码、完整阅读参考实现、列差异 | 你知道"哪里和正确做法不一样" |
| **Phase 3: 假设验证** | 提出一个具体假设，做最小改动验证 | 假设被证实或证伪 |
| **Phase 4: 修复实施** | 先写失败测试，再做单一修复，验证无回归 | 测试通过，问题消失，没引入新 Bug |

**关键纪律**：
- 不能跳过 Phase 1 直接修。
- Phase 3 一次只验证一个假设，不能"把 A 和 B 都改了试试看"。
- 如果修了 3 次都没好，必须停下来质疑架构，而不是继续试第 4 次。

### 3.2 Red Flags（红灯警报）

Skill 内置了一套"危险思维检测器"。如果你脑子里冒出以下想法，它会立刻红灯报警，要求你回到 Phase 1：

- "先临时修一下，以后再查根因"
- "我猜大概是 X 的问题，改改看"
- "这次改两个小地方一起测"
- "测试先不写了，我手动验证一下就行"
- "我已经试了两次，再试一次应该就行了"（这是第 3 次，该质疑架构了）

### 3.3 技术债务登记（V2.1 新增）

如果经过完整调查，问题确实是环境/时序/外部因素导致，暂时无法定位根因：

- Skill 会帮你生成一份技术债务记录。
- 自动记入 `progress.md` 的风险列表。
- 原流程继续执行，不会因为一个无法定位的问题卡住整个项目。

## 4. 使用方式（完整示例）

### 4.1 测试失败调试

**场景**：你刚写完一个功能，跑测试时报错了。

**对话：**

> **你**：测试失败了，帮我调试一下。
> ```
> Error: timeout of 5000ms exceeded
>     at test/user-service.test.ts:42:15
> ```
>
> **AI**：收到。启动 systematic-debugging，Phase 1 根因调查开始。
>
> **AI**：
> 1. **错误信息精读**：超时 5000ms，位置在 `user-service.test.ts:42`。
> 2. **复现确认**：这个测试每次跑都失败吗？
>
> **你**：是的，每次都在 42 行超时。
>
> **AI**：
> 3. **近期变更检查**：你最近改了什么？
>
> **你**：我刚在 `user-service.ts` 里加了一个数据库查询。
>
> **AI**：
> 4. **数据流追踪**：让我看看那个查询...
> ```typescript
> // user-service.ts:28
> const users = await db.query('SELECT * FROM users WHERE status = ?', [status]);
> ```
> 这个查询没有 LIMIT，如果 users 表数据量大，会拖慢响应。
>
> **AI**：Phase 1 结论：**根因是缺少 LIMIT 的全表查询导致响应超时。**
>
> **AI**：进入 Phase 3，形成假设："增加 LIMIT 100 后测试会通过"。
>
> **AI**：最小改动验证：在查询后加 `.limit(100)`，重新跑测试...
>
> **AI**：测试通过。假设证实。
>
> **AI**：进入 Phase 4：
> 1. 先写一个失败测试（验证无 LIMIT 时超时）。
> 2. 实施修复：增加 `LIMIT 100`。
> 3. 验证：所有测试通过，无回归。
>
> **AI**：调试完成。根因：全表查询无 LIMIT。已修复。

### 4.2 多组件系统问题

**场景**：CI 构建失败了，错误发生在签名阶段，但不确定是哪一层丢的证书。

**对话：**

> **你**：CI 构建在代码签名阶段失败了，帮我看看。
>
> **AI**：启动 systematic-debugging。这是一个多组件系统问题，Phase 1 需要加 instrumentation。
>
> **AI**：建议在以下三层加日志：
> 1. Workflow 层：检查 secrets 是否注入。
> 2. Build 脚本层：检查环境变量是否传递。
> 3. Signing 脚本层：检查 keychain 状态。
>
> **你**：[添加日志后重新跑 CI]
>
> **AI**：根据日志输出：
> - Workflow 层：`IDENTITY=SET` ✅
> - Build 脚本层：`IDENTITY not in environment` ❌
>
> **AI**：根因定位：**Workflow 的 secrets 没有传递到 Build 脚本的环境变量中。**
>
> **AI**：Phase 3 假设："在 build 脚本中显式导出 IDENTITY 可修复"。
>
> **你**：[修改后验证]
>
> **AI**：构建通过。修复完成。

### 4.3 3 次修复失败后质疑架构

**场景**：你已经试了两次修复一个状态同步问题，每次修复都导致新地方出问题。

**对话：**

> **你**：这个状态同步问题我修了两次都没好，每次修完别的地方又坏了。
>
> **AI**：检测到修复尝试次数 ≥ 3。根据 Iron Law，现在必须停止修复，进入 **Architecture Challenge**。
>
> **AI**：当前模式分析：
> - 第 1 次修复：改了 A 模块的缓存逻辑 → B 模块数据不一致。
> - 第 2 次修复：补了 B 模块的同步 → C 模块时序错乱。
> - 第 3 次修复：调整了 C 模块的触发时机 → A 模块又出问题了。
>
> **AI**：这是一个典型的**共享状态耦合**症状。三个模块通过隐式状态互相影响，任何局部修复都会破坏全局平衡。
>
> **AI**：建议：
> 1. 不要继续修症状了。
> 2. 与人类搭档讨论：是否应该引入显式状态机或事件总线来解耦？
> 3. 如果需要，我可以帮你起草一个重构提案。

### 4.4 根因无法定位时的技术债务

**场景**：一个偶发的时序问题，本地无法复现，只在 CI 的并行测试中偶尔出现。

**对话：**

> **你**：这个测试偶尔失败，大概 1/20 的概率，本地从没复现过。
>
> **AI**：启动 systematic-debugging。Phase 1 根因调查...
>
> **AI**：经过完整调查：
> - 错误信息不一致，有时超时，有时断言失败。
> - 本地和 CI 环境差异大（CPU 核心数、网络延迟）。
> - 加了 instrumentation 后，失败位置每次都不同。
>
> **AI**：结论：**这是环境依赖的时序问题，当前信息不足以定位根因。**
>
> **AI**：根据流程，现在将这个问题登记为技术债务，不阻塞当前流程：
> ```yaml
> risks:
>   - id: R-042
>     type: technical-debt
>     description: "[测试] 偶发并行测试失败 — 根因未定位，疑为 CI 环境时序敏感"
>     phase: unit-test
>     status: open
> ```
>
> **AI**：同时建议增加防御性处理：
> - 增加测试重试机制（明确标注为 flake 处理）。
> - 增加更详细的并行执行日志，等待下次失败时收集更多证据。
>
> **AI**：技术债务已记入 `progress.md`。你可以继续执行其他任务。

## 5. 输出产物说明

### 5.1 根因分析报告

调试完成后，你会得到一个清晰的结论：

- **根因是什么**：一句话说清楚。
- **证据链**：从现象到根因的推理路径。
- **修复方案**：具体改哪里、怎么改。
- **验证结果**：测试是否通过、有无回归。

### 5.2 技术债务记录

如果根因无法定位，你会得到：

- **债务 ID**：如 `R-042`，可在 `progress.md` 中追踪。
- **现象摘要**：便于后续识别。
- **建议的防御措施**：在找到根因前减少影响。

## 6. 常见问题

### Q1：这个流程会不会太慢？紧急 Bug 也要走四阶段吗？

** systematic 调试比 guess-and-check 更快。** 数据显示：随机修复平均 2-3 小时，系统调试平均 15-30 分钟。紧急情况下更容易猜错，流程反而更重要。

### Q2：我可以跳过 Phase 2（模式分析）吗？我对代码很熟悉。

不可以。"熟悉"是直觉，不是证据。Phase 2 强制你与参考实现对比，很多 Bug 正是因为"我以为这里和那里一样"导致的。

### Q3：3 次修复失败就一定要质疑架构吗？也许第 4 次就对了。

**必须质疑。** 3 次失败说明你在打地鼠，不是在解决问题。此时最危险的念头就是"再试一次"。停下来讨论架构，通常能一次性解决根本问题。

### Q4：技术债务登记是不是在逃避问题？

不是。95% 的"无根因"其实是调查不彻底，这个 Skill 会强制你完成完整流程后才允许登记。真正环境依赖的偶发问题，强行假修复反而更危险——登记为债务、增加监控、等待更多证据，是更专业的做法。

### Q5：调试过程中可以问人类帮忙吗？

随时可以。Phase 3 明确说了："不懂就承认，Ask for help"。这个 Skill 反对的是"不懂装懂瞎猜"，不是"寻求帮助"。

## 7. 快速参考卡

### 7.1 触发口令

| 你想做什么 | 怎么说 |
|-----------|--------|
| 测试失败调试 | "测试失败了，帮我调试一下。" |
| 线上 Bug 排查 | "线上出现了这个报错，帮我找根因。" + 贴日志 |
| 性能问题 | "这个接口变慢了，帮我分析一下。" |
| 构建失败 | "CI 构建失败了，帮我看看。" |
| 集成问题 | "集成测试通不过，不确定哪里的问题。" |
| 已试多次没好 | "我已经试了两次修复都没成功。" |
| 登记技术债务 | "这个问题根因实在找不出来，先登记为技术债务吧。" |

### 7.2 四阶段速查

| 阶段 | 关键问题 | 禁止做的事 |
|------|----------|-----------|
| Phase 1 | "为什么会出这个问题？" | 不许提议修复 |
| Phase 2 | "正确做法是什么样的？差异在哪？" | 不许凭直觉跳过对比 |
| Phase 3 | "我的假设对吗？" | 不许一次改多个地方 |
| Phase 4 | "修复后测试通过了吗？" | 不许夹带其他改动 |

### 7.3 Red Flag 速查

| 危险想法 | 正确做法 |
|----------|----------|
| "先临时修一下" | 回 Phase 1，找到根因再修 |
| "我猜是 X 的问题" | 写成假设，验证后再修 |
| "改两处一起测" | 一次只改一处 |
| "不写测试了，手动验" | 必须先写失败测试 |
| "再试一次应该就行了"（≥3次） | 停止，质疑架构 |

---

> 💡 **使用心法**：`systematic-debugging` 不是让你变慢，而是让你**一次做对**。 Debugging 中最贵的不是调查时间，而是"修错了 → 引发新问题 → 再修 → 再出问题"的无限循环。养成习惯：**看到 Bug → 启动四阶段 → 找到根因 → 一次修复**。
