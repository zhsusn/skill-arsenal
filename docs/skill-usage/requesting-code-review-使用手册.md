# requesting-code-review（代码审查）使用手册

> 版本：V2.1  
> 适用 Skill：`skills/sdlc/requesting-code-review`  
> 一句话定位：**在代码合入前派个专业审查团队帮你抓虫，发布前再最后把关一次。**

---

## 1. 这是什么？

`requesting-code-review` 是你的「代码质检官」。它不会写代码，但特别擅长挑代码的毛病——而且挑得很系统、很全面。

V2.1 版本有两个核心升级：
1. **UAT 通过后强制触发**：就算功能验收通过了，发布前也必须最后再审查一次代码，防止"功能对了、代码烂了"的情况溜进生产环境。
2. **强制输出结构化报告**：每次审查都会生成一份 `code-review-report.md`，有结论、有问题分级、有修复建议，可以直接贴到发布清单里。

你可以把它理解为一个**永不疲倦、不讲情面、但会给出具体修复方案**的代码审查员。

---

## 2. 适用场景

以下场景，强烈建议使用：

- ✅ 一个功能开发完了，准备合并到主干之前。
- ✅ 执行计划（Executing Plans）走到"代码审查"步骤时。
- ✅ UAT 已经通过，准备发布上线前的**最后一道质量门**。
- ✅ 同事临时丢给你一段代码，想快速听听意见。
- ✅ 项目交付前，需要对全量代码做一次兜底审查。
- ✅ 线上出了 Bug，热修复后需要紧急 review。

**不适合的场景**：
- ❌ 完全空白的项目初始化（没有代码可审）。
- ❌ 仅修改了文档/配置，无逻辑代码变更（虽然也能审，但有点大材小用）。

## 3. 核心功能

### 3.1 四种审查模式，按需选用

| 模式 | 什么时候用 | 特点 |
|------|-----------|------|
| **Subagent-Driven** | 大型变更（改了很多文件） | 同时派多个专家子代理并行审查（安全、架构、性能、可维护性各一个），然后汇总结论 |
| **Executing Plans** | 你正在按执行计划推进项目 | 自动读取计划中的代码范围，审查完自动把修复任务排进计划里 |
| **Ad-Hoc** | 临时、突发、小片段 | 随手粘贴代码或 PR 链接，快速出结论 |
| **Project Delivery** | 项目收尾或技术交接 | 审查整个项目代码基线，而不仅仅是这次改了什么 |

### 3.2 三级问题分级

审查发现的问题分成三级，一目了然：

- 🔴 **Blocker（阻塞）**：有安全漏洞、可能丢数据、架构原则被违反、严重性能问题。**这个代码现在不能合，也不能发。**
- 🟡 **Major（重要）**：可维护性差、边界条件没处理、错误处理不完整。**建议修，修好了更稳。**
- 🟢 **Minor（轻微）**：命名不太对、缺注释、格式不统一。**顺手改改最好，不改也不拦你。**

### 3.3 结构化审查报告（V2.1 强制输出）

每次审查结束，你都会拿到一份 `code-review-report.md`，里面固定包含：

1. **总体结论** —— 通过 / 有条件通过 / 拒绝，一句话说清楚。
2. **阻塞性问题** —— 必须修。
3. **重要问题** —— 建议修。
4. **轻微问题** —— 可以修。
5. **亮点** —— 做得好的地方，值得保持甚至推广。
6. **UAT 交叉验证** —— UAT 发现的问题，在代码层面到底修没修好？（发布前审查时特别有用）
7. **下一步行动** —— 清晰的待办清单，谁修、修什么、大概多久。

### 3.4 UAT 交叉验证（V2.1 新增）

发布前审查时，Skill 会自动把 UAT 阶段发现的问题和代码变更做交叉比对：

- 这个问题在代码里修了吗？
- 修得彻底吗？还是只修了表面症状？
- 有没有 UAT 问题在代码里完全没体现，根因还没触及？

这个功能专治"UAT 过了就万事大吉"的幻觉。

## 4. 使用方式（完整示例）

### 4.1 基本用法：PR 合并前审查

**场景**：你刚提交了一个 PR，改动了用户登录模块，准备合并。

**对话：**

> **你**：帮我审查一下这个 PR，准备合并。
>
> **AI**：收到。请提供以下信息（或我将尝试自动提取）：
> 1. 变更描述（DESCRIPTION）：这次改了什么？为什么改？
> 2. 关联需求/计划（PLAN_OR_REQUIREMENTS）：对应哪条需求？
> 3. 代码范围（BASE_SHA .. HEAD_SHA）：从哪个版本改到哪个版本？
>
> **你**：
> - 描述：修复用户登录时的并发会话冲突问题，引入分布式锁。
> - 关联需求：PRD-2026-LOGIN-003 登录安全性增强。
> - 范围：`a1b2c3d`..`e4f5g6h`
>
> **AI**：正在启动 Subagent-Driven 审查模式。已分派：安全审计代理、架构评审代理、性能检查代理。
> ...（分析中）...
>
> **AI**：审查完成。报告已生成 `code-review-report.md`。
>
> **裁决：CONDITIONAL_APPROVE（无 Blocker，但有 2 个 Major）**
>
> ---
> **🟡 Major 示例：**
> #### [ARCH-001] 分布式锁未设置过期时间
> - **文件**：`auth/lock_manager.py:45`
> - **代码**：`redis_client.set(lock_key, request_id)`
> - **问题**：未设置 TTL，若服务异常退出会导致死锁。
> - **建议**：增加 `nx=True, ex=30` 参数，并配套续期机制。
>
> **下一步行动**：
> 1. [MAJOR] 为分布式锁增加过期时间与续期机制。
> 2. [MAJOR] 补充并发测试用例覆盖边界情况。
> 3. 修复后对我说"已修复，重新审查"。

### 4.2 发布前强制审查

**场景**：UAT 已经通过，明天要发布，项目经理要求出具代码审查报告。

**对话：**

> **你**：UAT 通过了，准备明天发布，帮我做发布前的代码审查。
>
> **AI**：收到，正在执行 **PRE_RELEASE** 门控审查（V2.1 强制触发）。
> 已加载 UAT 遗留问题清单，启动 UAT 交叉验证...
>
> **AI**：审查完成。报告已生成 `code-review-report.md`。
>
> **裁决：APPROVE**
> - Blocker：0 | Major：1（已记录） | Minor：3
> - UAT 交叉验证：5 个 UAT 问题全部在代码层面有对应修复痕迹，无未触及根因项。
>
> 代码可以进入发布流程。报告已准备就绪，可作为发布清单附件。

### 4.3 临时审查：同事丢来一段代码

**对话：**

> **你**：帮我看看这段代码有没有问题。
> ```python
> def transfer_money(from_account, to_account, amount):
>     db.execute(f"UPDATE accounts SET balance = balance - {amount} WHERE id = {from_account}")
>     db.execute(f"UPDATE accounts SET balance = balance + {amount} WHERE id = {to_account}")
> ```
>
> **AI**：正在执行 Ad-Hoc 轻量级审查...
>
> **AI**：发现 **1 个 BLOCKER**。
>
> 🔴 **Blocker**
> #### [SEC-001] SQL 注入风险
> - **位置**：第 2-3 行
> - **问题**：直接使用字符串拼接构造 SQL 语句，`amount`、`from_account`、`to_account` 可被注入恶意 SQL。
> - **建议**：使用参数化查询：`db.execute("UPDATE accounts SET balance = balance - ? WHERE id = ?", (amount, from_account))`
> - **额外建议**：该转账函数缺少事务包裹，若第二条 SQL 失败会导致资金丢失。建议增加 `BEGIN TRANSACTION` / `COMMIT` / `ROLLBACK`。
>
> **AI**：这段代码**不能合入**。请修复 SQL 注入并补充事务控制后再次提交审查。

### 4.4 与执行计划集成

**场景**：你正在使用 `executing-plans` Skill 推进一个多步骤计划，当前步骤是"代码审查"。

**对话：**

> **你**：继续执行计划，进入代码审查步骤。
>
> **AI**：计划步骤 5/8：代码审查。已自动读取计划上下文：
> - 描述：实现订单退款功能
> - 关联需求：PRD-ORDER-REFUND
> - 代码范围：计划附件中的 `base_sha` 和 `head_sha`
>
> **AI**：正在启动审查...
> ...（输出报告）...
>
> **AI**：审查完成。已根据报告中的 Next Actions 自动生成计划后续步骤：
> - 步骤 6：修复 Blocker（预计 2 小时）
> - 步骤 7：回归测试
> - 步骤 8：重新审查并合并

## 5. 输出产物说明

### 5.1 code-review-report.md

这是 `requesting-code-review` 的核心交付物。文件名固定（或带时间戳后缀），可直接用于：

- **PR 附件**：贴在 Pull Request 描述里，供团队 Reviewer 参考。
- **发布清单前置输入**：`release-management` Skill 会读取这份报告，确认没有未关闭的 Blocker 才允许发布。
- **审计存档**：作为代码质量的历史记录，留存备查。

### 5.2 报告关键字段解读

| 字段 | 含义 |
|------|------|
| **裁决（Verdict）** | `APPROVE` = 直接过；`CONDITIONAL_APPROVE` = 修完 Major 再过；`REJECT` = 有 Blocker，先修 |
| **风险等级** | LOW / MEDIUM / HIGH，帮你判断这个 PR 的"危险气味" |
| **UAT 交叉验证** | 发布前审查时重点看这里，确认 UAT 问题真的在代码里修好了 |
| **下一步行动** | 可直接复制到任务管理工具（如 Jira/Trello）作为子任务 |

## 6. 常见问题

### Q1：为什么 UAT 通过了还要审查代码？

因为"功能验收通过"不等于"代码质量合格"。UAT 验证的是"用户视角的功能正确性"，代码审查验证的是"工程视角的质量可持续性"。V2.1 强制在发布前再加一道门，就是为了防止"功能对了但代码埋雷"的情况上线。

### Q2：Blocker 可以忽略吗？

**绝对不可以。** Blocker 意味着存在安全风险、数据风险或架构风险。如果你认为某个 Blocker 判定有误，应该提供反驳证据（如"这里使用了 ORM 自动转义，不存在注入"），由审查引擎重新评估。而不是直接忽略。

### Q3：我没有 Git SHA，只想审查一段代码，怎么办？

直接用 **Ad-Hoc 模式**。粘贴代码片段即可，不需要提供 BASE_SHA / HEAD_SHA。Skill 会自动识别为轻量级临时审查。

### Q4：报告里的"亮点"有什么用？

不只是为了夸你。亮点部分会指出写得好的模式，建议推广到团队其他模块。对于技术 Leader 来说，这是发现团队最佳实践的渠道。

### Q5：UAT 交叉验证说"未触及根因"是什么意思？

意思是：UAT 发现了一个问题，代码变更里也改了一块相关代码，但改的是表面症状（比如多加了个判断），而不是导致问题的根本原因（比如底层状态机设计缺陷）。这种情况建议深入重构，而不是打补丁。

### Q6：审查一个大 PR 要等很久吗？

Subagent-Driven 模式下，多个子代理是并行工作的，所以比单线程审查快。但如果 PR 真的超大（>50 文件），建议先拆分成小 PR，审查效率和质量都会更好。

### Q7：code-review-report.md 存在哪里？

默认输出在对话中。你可以说"保存审查报告"，AI 会写入当前工作目录。建议留存命名：`code-review-report-{日期}.md`。

| 你想做什么 | 怎么说 |

| PR 合并前审查 | "帮我审查这个 PR，准备合并。" |
| 发布前强制审查 | "UAT 通过了，做发布前的代码审查。" |

| 重新审查 | "已修复，重新审查。" |
| 保存报告 | "保存审查报告为文件。" |

### 7.2 裁决结果速查

| 裁决 | 含义 | 你能做什么 |
|------|------|-----------|
| **APPROVE** | 代码质量达标 | 放心合入 / 发布 |
| **CONDITIONAL_APPROVE** | 无 Blocker，但有 Major | 修完 Major 后合入；或记录接受风险的理由 |
| **REJECT** | 存在 Blocker | 必须修复 Blocker 后重新审查 |

### 7.3 四种模式选择速查

| 场景 | 选哪个模式 |
|------|-----------|
| 改了很多文件，需要全面审查 | Subagent-Driven |
| 正在按执行计划推进 | Executing Plans |
| 临时贴代码、快速问意见 | Ad-Hoc |
| 项目收尾、全量兜底 | Project Delivery |

### 7.4 Placeholder 速查

| 占位符 | 你在对话中需要提供 |
|--------|-------------------|
| DESCRIPTION | "这次改了什么，为什么改" |
| PLAN_OR_REQUIREMENTS | "对应哪条需求/计划" |
| BASE_SHA / HEAD_SHA | "从哪个版本改到哪个版本"（或提供 PR 链接） |
| UAT_ISSUES | UAT 阶段的问题清单（发布前审查时自动加载） |
