# Monitoring Analysis（线上监控分析）使用手册

> 版本：V2.4
> 适用 Skill：`skills/sdlc/monitoring-analysis`
> 一句话定位：**项目上线了？这只是开始。周期性读取监控数据，评估健康度，把线上问题转化为下一迭代的需求输入。**

---

## 1. 这是什么？

`monitoring-analysis` 是你的"线上健康医生"。

项目上线后，它不是" set it and forget it "，而是周期性（建议每周一次）帮你：

- 读取监控规则基线和运行时数据，评估系统健康度
- 识别性能退化、错误率上升、业务指标波动等风险信号
- 生成结构化的健康报告（`monitoring-dashboard.md`）
- 提炼产品改进建议，输出 `feedback-loop.md` 反哺下一变更的 `brainstorming`

**核心定位**：不是替代运维工具（Prometheus/Grafana/Sentry），而是**帮你读懂数据、提炼洞察、闭环改进**。

---

## 2. 适用场景

以下场景，强烈建议使用：

- ✅ `finish` 归档完成后，进入周期性运维阶段。
- ✅ 需要生成本周/本迭代的系统健康报告。
- ✅ 告警触发后，需要分析问题根因和影响范围。
- ✅ 准备规划下一迭代，需要基于线上数据确定优化方向。

**不适合的场景**：
- ❌ 需要实时告警响应（请使用专业监控工具如 PagerDuty）。
- ❌ 需要深度根因分析（请结合 `systematic-debugging`）。
- ❌ 项目尚未上线（无运行时数据可分析）。

## 3. 核心功能

### 3.1 三阶段流水线

| 阶段 | 做什么 | 说明 |
|------|--------|------|
| **Phase 1** | 读取基线与数据 | 读取 `monitoring-rules.yaml` + 用户提供的运行时数据 |
| **Phase 2** | 健康度评估 | 基础设施 / 应用性能 / 业务健康 三层评估 |
| **Phase 3** | 生成报告与闭环 | 输出 `monitoring-dashboard.md` + `feedback-loop.md` |

### 3.2 三层健康评估模型

| 层级 | 指标示例 | 权重 | 典型关注点 |
|------|----------|------|-----------|
| 基础设施 | CPU、内存、磁盘、网络 | 20% | 资源是否充足 |
| 应用性能 | QPS、P50/P99 延迟、错误率 | 40% | 服务是否稳定 |
| 业务健康 | 转化率、支付成功率、DAU | 40% | 产品是否健康 |

**状态判定规则**：

| 状态 | 标准 |
|------|------|
| 🟢 健康 | 指标在阈值范围内，环比波动 < 5% |
| 🟡 关注 | 指标接近阈值（80% 阈值）或环比波动 5-15% |
| 🔴 风险 | 指标超过阈值或环比波动 > 15% 或连续两周同向恶化 |

### 3.3 告警复盘

- 统计本周告警次数和级别分布
- 识别告警疲劳（同一告警一周内触发 > 3 次且均为误报）
- 分析告警根因和处理结果

### 3.4 Feedback Loop

基于健康报告中的异常项和趋势变化，生成 `feedback-loop.md`：

- 正向反馈（保持）：业务指标增长、稳定性提升
- 负向信号（需关注）：性能退化、错误率上升
- 产品改进建议：优先级 P0/P1/P2，附数据依据
- 技术债务信号：重复告警、临时修复
- 输入到 `brainstorming` 的提示语

## 4. 使用方式（完整示例）

### 4.1 常规巡检

**场景**：每周五下午，生成本周健康报告。

**对话：**

> **你**：生成本周健康报告。
>
> **AI**：收到。启动 `monitoring-analysis` Skill。
>
> **AI**：**Phase 1: 读取基线与数据**
> 已读取 `ops/monitoring-rules.yaml`。
> 请提供本周运行时数据（或粘贴关键指标摘要）。
>
> **你**：[粘贴 Prometheus/Grafana 关键指标截图或摘要]
> - API Gateway: QPS 1200, P99 680ms, 错误率 0.3%
> - Order Service: QPS 800, P99 420ms, 错误率 0.1%
> - CPU 均值 45%, 内存 60%
> - 本周告警 5 次（warning 4 次, critical 1 次）
>
> **AI**：**Phase 2: 健康度评估**
> | 维度 | 状态 | 关键指标 |
> |------|------|----------|
> | 基础设施 | 🟢 健康 | CPU 45%, 内存 60% |
> | 应用性能 | 🟡 关注 | API Gateway P99 680ms（阈值 500ms） |
> | 业务健康 | 🟢 健康 | 订单转化率 3.2%（超基线） |
> | **综合健康度** | 🟡 良好 | 建议关注 API Gateway 延迟 |
>
> **AI**：**Phase 3: 生成报告与闭环**
> 已生成：
> - `ops/monitoring-dashboard-20260512.md`
> - `openspec/feedback/feedback-loop.md`
>
> **Feedback Loop 摘要**：
> - 负向信号：API Gateway P99 持续超过阈值
> - 改进建议：P1 — 启动性能优化专项，目标 P99 < 500ms
> - 技术债务：api-gateway_HighP99Latency 告警本周触发 2 次

### 4.2 告警响应分析

**场景**：告警触发后，需要快速分析影响。

**对话：**

> **你**：api-gateway 告警触发了，分析一下。
>
> **AI**：收到。基于最新监控数据执行分析。
>
> **AI**：**分析结果**：
> - 告警：api-gateway_HighP99Latency（P99 680ms > 阈值 500ms）
> - 持续时间：12 分钟
> - 根因推测：下游 order-service 响应延迟增加
> - 影响范围：用户下单流程可能变慢
> - 建议：检查 order-service 最近是否有变更

### 4.3 Feedback Loop 输入 Brainstorming

**对话：**

> **你**：基于 feedback-loop.md 启动下一迭代规划。
>
> **AI**：读取 `openspec/feedback/feedback-loop.md`...
>
> **AI**：上一周期关键信号：
> - API Gateway P99 延迟持续恶化（680ms > 500ms 阈值）
> - 建议：启动性能优化专项
>
> **AI**：触发 `brainstorming`...
> "基于监控反馈，API Gateway P99 延迟需优化至 500ms 以下，探索优化方向。"

## 5. 输出产物说明

### 5.1 monitoring-dashboard.md

分层健康报告，包含：

- 执行摘要（综合健康度）
- 基础设施层详情
- 应用性能层详情
- 业务指标层详情
- 告警复盘
- 风险评估与建议

### 5.2 feedback-loop.md

反馈闭环文档，包含：

- 正向反馈（保持）
- 负向信号（需关注）
- 产品改进建议（含优先级 P0/P1/P2）
- 技术债务信号
- 输入到 `brainstorming` 的提示语

**时效性**：覆盖最近 2-4 周，过期反馈归档到 `openspec/feedback/archive/`。

## 6. 常见问题

### Q1：AI 能直接读取我的 Prometheus/Grafana 吗？

通常不能。AI 一般无法直接访问生产环境的内网监控系统。你需要手动提供关键指标摘要（截图、导出数据或文字描述）。AI 的职责是**分析数据**而非**采集数据**。

### Q2：多久执行一次 monitoring-analysis？

| 场景 | 频率 |
|------|------|
| 常规巡检 | 每周一次 |
| 迭代收尾 | 每迭代一次 |
| 告警响应 | 事件驱动 |
| 版本发布后 | 发布后 24h / 72h |

### Q3：阈值是固定的吗？

不是。`monitoring-rules.yaml` 中的阈值是设计阶段确定的基线，实际运行中可能需要调整。健康报告中应标注"阈值最后更新时间"，建议每季度回顾一次。

### Q4：单次波动需要关注吗？

不需要过度反应。环比变化在 ±5% 范围内通常属于正常波动。只有**连续两周同向趋势**才值得预警。

### Q5：feedback-loop.md 会过期吗？

会。`feedback-loop.md` 应覆盖最近 2-4 周的监控周期。过期的反馈应归档到 `openspec/feedback/archive/`，避免 `brainstorming` 阶段读取过时信息。

### Q6：发现阈值长期不适用怎么办？

在 `feedback-loop.md` 中标注"建议调整 monitoring-rules.yaml 中 X 项阈值"，但不要直接修改 YAML。阈值调整应经过团队评审。

### Q7：业务指标和应用指标哪个更重要？

业务指标优先。相比 CPU/内存，转化率、支付成功率、用户留存更能反映产品真实健康度。健康报告的结论应以业务层指标为首要权重。

## 7. 快速参考卡

### 7.1 触发口令

| 你想做什么 | 怎么说 |
|-----------|--------|
| 生成本周健康报告 | "生成本周健康报告" / "执行监控分析" |
| 分析告警 | "分析 api-gateway 告警" |
| 查看 feedback-loop | "打开 feedback-loop.md" |
| 启动下一迭代 | "基于 feedback-loop 启动 brainstorming" |

### 7.2 数据提供模板

向 AI 提供监控数据时，建议按以下格式：

```text
【基础设施】
- CPU 均值: X%, 峰值: Y%
- 内存均值: X%, 峰值: Y%
- 磁盘使用率: X%

【应用性能】
- API Gateway: QPS X, P50 Yms, P99 Zms, 错误率 W%
- Order Service: QPS X, P50 Yms, P99 Zms, 错误率 W%

【业务指标】
- DAU: X（环比 ±Y%）
- 订单转化率: X%（环比 ±Y%）
- 支付成功率: X%（环比 ±Y%）

【告警历史】
- 本周告警 N 次（critical: X, warning: Y）
- 主要告警：...
```

### 7.3 健康度判定速查

| 现象 | 状态 | 建议 |
|------|------|------|
| 指标在阈值内，波动 < 5% | 🟢 健康 | 保持观察 |
| 指标接近阈值或波动 5-15% | 🟡 关注 | 持续观察，必要时排查 |
| 指标超阈值或波动 > 15% | 🔴 风险 | 立即排查，启动修复 |
| 同一告警一周 > 3 次误报 | 🟡 告警疲劳 | 建议上调阈值或优化条件 |

> 💡 **使用心法**：`monitoring-analysis` 是整个交付链路的"闭环终点"。很多团队上线后就散了，但专业的团队知道：**上线只是开始，监控和改进才是常态**。记住：没有 feedback-loop 的项目，同一个问题会反复出现。养成习惯：**每周看一次健康报告，把数据变成下一迭代的行动**。
