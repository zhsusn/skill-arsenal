## 概述

### 定位

`monitoring-analysis` 是 **SDLC 阶段 12（线上监控）** 的周期性 Skill，职责是：

> 基于 `monitoring-setup` 生成的监控规则基线和运行时数据，评估系统健康度、识别潜在风险、提炼产品改进建议，产出 `feedback-loop.md` 反哺下一变更的 `brainstorming`。

### 核心差异化

与 `monitoring-setup`（一次性规则生成）形成互补：`monitoring-analysis` 是**规则消费与调优建议**（周期性）。

| 维度 | monitoring-setup | monitoring-analysis |
|---|---|---|
| 执行频次 | 一次性（每变更一次） | 周期性（每周/每迭代/事件驱动） |
| 核心职责 | 生成监控规则 YAML | 读取运行时数据，评估健康度 |
| 输出 | `monitoring-rules.yaml` | `monitoring-dashboard.md` + `feedback-loop.md` |
| 与 SDLC 衔接 | Gate 2 设计冻结 | finish 后闭环反馈到 brainstorming |

## 处理逻辑

### 三阶段流水线

#### Phase 1: 读取基线与数据

**基线读取**：
- `monitoring-rules.yaml` 中的阈值定义（作为评估基准）
- `alerting_rules` 中的告警配置
- `business_metrics` 中的业务埋点定义

**数据读取（用户提供）**：
- 基础设施层：CPU、内存、磁盘、网络
- 应用层：QPS、延迟分位值、错误率
- 业务层：转化率、活跃用户数、订单量
- 告警历史：本周触发次数、级别、恢复时间

#### Phase 2: 健康度评估

**三层评估模型**：

| 层级 | 指标示例 | 权重 |
|------|----------|------|
| 基础设施 | CPU、内存、磁盘 | 20% |
| 应用性能 | QPS、P99 延迟、错误率 | 40% |
| 业务健康 | 转化率、支付成功率、DAU | 40% |

**状态判定规则**：

| 状态 | 判定标准 |
|------|----------|
| 🟢 健康 | 指标在阈值范围内，环比波动 < 5% |
| 🟡 关注 | 指标接近阈值（80% 阈值）或环比波动 5-15% |
| 🔴 风险 | 指标超过阈值或环比波动 > 15% 或连续两周同向恶化 |

**告警复盘**：
- 统计本周告警次数和级别分布
- 识别告警疲劳（同一告警一周内触发 > 3 次且均为误报）
- 分析告警根因和处理结果

#### Phase 3: 生成报告与闭环

**健康报告** (`monitoring-dashboard.md`)：
1. 执行摘要（综合健康度）
2. 基础设施层详情
3. 应用性能层详情
4. 业务指标层详情
5. 告警复盘
6. 风险评估与建议

**反馈闭环** (`feedback-loop.md`)：
1. 正向反馈（保持）
2. 负向信号（需关注）
3. 产品改进建议（含优先级）
4. 技术债务信号
5. 输入到 brainstorming 的提示语

## 输入输出规格

### 输入

| 输入项 | 类型 | 来源 | 说明 |
|--------|------|------|------|
| 监控规则基线 | YAML | `ops/monitoring-rules.yaml` | 阈值定义与采集目标 |
| 运行时数据 | 多格式 | 外部监控系统 | 错误率、延迟、QPS、资源使用率 |
| 埋点数据 | 多格式 | 外部分析系统 | 用户行为、业务转化漏斗 |
| 告警历史 | 多格式 | 外部告警系统 | 本周触发记录 |
| 版本信息 | Markdown | `archive-confirmation.md` | 当前线上版本 |

### 输出

| 输出项 | 类型 | 路径 | 说明 |
|--------|------|------|------|
| 健康报告 | Markdown | `ops/monitoring-dashboard-{日期}.md` | 分层健康评估 |
| 反馈闭环 | Markdown | `openspec/feedback/feedback-loop.md` | 产品改进建议 |

## Feedback Loop 机制

### 闭环流程

```
monitoring-analysis
    └── feedback-loop.md
            └── brainstorming（下一变更）
                    └── prd-generation
                            └── ...（SDLC 循环）
                                    └── finish
                                            └── monitoring-analysis（验证改进效果）
```

### feedback-loop.md 结构

```markdown
# Feedback Loop

## 正向反馈
- {业务指标增长、稳定性提升}

## 负向信号
- {性能退化、错误率上升}

## 产品改进建议
1. **{标题}** — 优先级 P0/P1/P2 — 依据：...

## 技术债务信号
- {重复告警、临时修复}

## 输入 brainstorming
/skill:brainstorming 基于 feedback-loop.md ...
```

### 时效性管理

- `feedback-loop.md` 覆盖最近 2-4 周
- 过期反馈归档到 `openspec/feedback/archive/`
- 每季度清理一次 archive 目录

## 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| **AI 是否直接采集监控数据** | 否，由用户提供数据摘要 | AI 通常无法直接访问生产监控系统的内网接口 |
| **健康度评估权重** | 业务层 40% > 应用层 40% > 基础设施 20% | 业务指标更能反映产品真实健康度 |
| **阈值漂移处理** | 在报告中标注建议调整，但不直接修改 YAML | 保持 monitoring-setup 的一次性原则 |
| **波动容忍度** | 单次 ±5% 为正常，连续两周同向趋势才预警 | 避免过度反应 |
| **feedback-loop 时效** | 2-4 周，过期归档 | 确保 brainstorming 读取的信息不过时 |
