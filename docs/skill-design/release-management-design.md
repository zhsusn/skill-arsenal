## 概述

### 定位

`release-management` 是 **SDLC 阶段 10.5（上线发布）** 的核心 Skill，职责是：

> 基于 UAT 报告、代码审查报告和回滚方案，生成发布清单与发布说明，辅助人工完成最终发布决策。**AI 不执行生产发布。**

### 核心差异化

与开源社区的"DevOps 自动化"Skill 不同，`release-management` 明确采用**人工最终决策模式**——AI 负责文档生成和风险评估，生产环境的发布操作必须由人工执行。

| 维度 | DevOps 自动化型 | release-management（人工决策型） |
|---|---|---|
| 发布执行 | AI 自动执行部署命令 | AI 只生成检查清单，人工执行发布 |
| 风险承担 | AI 承担部署风险 | 人工承担发布决策风险，AI 提供信息支持 |
| 合规审计 | 自动化日志 | release-checklist.md 作为不可篡改的审计依据 |

## 处理逻辑

### 四阶段流水线

#### Phase 1: 读取输入与风险评估

**输入校验（硬性阻断）**：

| 输入项 | 校验规则 | 失败处理 |
|--------|----------|----------|
| uat-report.md | 结论为"通过"或"有条件通过" | 拒绝，提示修复 UAT 问题 |
| code-review-report.md | 阻塞性问题数 = 0 | 拒绝，提示修复代码问题 |
| rollback-plan.md | 存在且包含回滚步骤 | 标记风险，要求人工补充 |
| monitoring-rules.yaml | 存在且已生效 | 标记风险，要求确认告警通道 |

**风险评估矩阵**：

| 维度 | 权重 | 说明 |
|------|------|------|
| UAT 结论 | 30% | 是否通过 |
| 代码审查 | 25% | 阻塞性问题是否清零 |
| 回滚方案 | 20% | 是否可操作 |
| 监控就绪 | 15% | 规则是否生效 |
| 遗留问题 | 10% | 是否影响发布 |

#### Phase 2: 生成发布清单

`release-checklist.md` 包含四段：
1. **预发布检查**：6 项硬性检查（代码审查、UAT、回滚、监控、配置、数据库）
2. **发布步骤**：7 步标准发布流程（窗口确认 → 数据库迁移 → 部署 → 健康检查 → 抽样验证 → 监控确认 → 通知）
3. **回滚触发条件**：明确什么情况下必须立即回滚
4. **发布后验证**：3 项抽样验证

#### Phase 3: 生成发布说明

`release-notes.md` 遵循 Keep a Changelog 风格，包含：
- 变更概要
- 新增 / 修复 / 变更
- 已知问题（来自 UAT 遗留）
- 回滚方案引用
- 监控摘要
- 关联文档链接

#### Phase 4: 人工最终决策

AI 输出提示语后进入阻塞状态，等待人工明确信号：
- "发布成功" → 触发 `finish`
- "发布失败/回滚" → 记录事件，等待后续指令
- "暂不发布" → 保持等待

## 输入输出规格

### 输入

| 输入项 | 类型 | 来源 | 说明 |
|--------|------|------|------|
| UAT 报告 | Markdown | `uat/uat-report.md` | Gate 3 签字结论 |
| 代码审查报告 | Markdown | `code-review-report.md` | 阻塞性问题清零确认 |
| 回滚方案 | Markdown | `design/rollback-plan.md` | 阶段 3 产出 |
| 监控规则 | YAML | `ops/monitoring-rules.yaml` | 生效状态确认 |
| Git 状态 | 命令输出 | Git 仓库 | 分支、commit SHA |

### 输出

| 输出项 | 类型 | 路径 | 说明 |
|--------|------|------|------|
| 发布检查清单 | Markdown | `openspec/changes/{变更名}/release-checklist.md` | 发布前检查与步骤 |
| 发布说明 | Markdown | `openspec/changes/{变更名}/release-notes.md` | 团队/用户 facing |
| 风险评估 | Markdown | `openspec/changes/{变更名}/release-risk-assessment.md` | 可选 |

## 安全设计

### 绝对约束（红线）

| 约束 | 说明 | 违反后果 |
|------|------|----------|
| 严禁 AI 自动发布 | AI 不得执行任何生产环境部署命令 | 严重违规，立即停止 |
| 严禁带病发布 | 存在未清零阻塞性问题时拒绝生成清单 | 防止质量事故 |
| 严禁推断发布成功 | 必须等待人工明确信号 | 防止误判 |

### 安全输出规范

`release-notes.md` 禁止包含：
- 内网 IP、数据库连接串
- API Key、Token、密码
- 详细的服务器架构图（可提及组件名，不可暴露拓扑）

## 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| **AI 是否执行发布命令** | 否 | 生产发布涉及不可逆操作，风险应由人类承担和决策 |
| **发布清单是否可跳过** | 否 |  checklist 是发布审计的核心依据，缺失即视为违规发布 |
| **回滚方案可操作性要求** | 必须包含具体步骤 | "必要时回滚"等模糊描述不可接受 |
| **数据库 DDL 变更标注** | 单独标注为不可逆操作 | DDL 回滚复杂度高，需人工二次确认 |
| **发布后验证范围** | 抽样验证（1-2 个 P0 链路） | 全量 UAT 已执行，发布后只需确认无回归 |

## 风险与规避

| 风险 | 规避方法 |
|------|----------|
| AI 误推断发布成功 | 明确信号词："发布成功"；禁止基于 git 状态推断 |
| 发布清单被人工跳过 | checklist 设计为不可跳过的审计文档 |
| 回滚方案不可操作 | Phase 1 校验 rollback-plan.md，含糊内容标记风险 |
| 监控告警未触达 | 发布清单中要求人工确认告警通道配置 |
| 敏感信息泄露到 release-notes | 安全输出规范：禁止包含凭证和内网地址 |
